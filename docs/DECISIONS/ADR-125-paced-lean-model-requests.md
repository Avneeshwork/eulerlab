# ADR-125: Model requests are paced to the host's per-minute limit, and the knowledge agent sends fewer, smaller ones

- **Context:** The knowledge agent failed live on Groq's free tier (T-4402): its tool loop sent rounds back to back, each re-sending all 17 tool descriptions and every earlier result, about 18,000 tokens a minute against a limit of 8,000; and gpt-oss-120b called a tool on the last round, which offers none (research 143). The operator asked to cut its usage.
- **Options:** (a) Move the knowledge agent to a paid model. (b) Wait between rounds by a fixed delay. (c) Pace each request to the provider's `tokens_per_minute`, and make the knowledge agent's requests fewer and smaller.
- **Choice:** (c). `chat.pace` waits only for the tokens a request lacks, refilling at the limit's rate and correcting from Groq's `x-ratelimit-remaining-tokens`; it applies to every caller of `chat._post` (AI tab, Telegram, agents) for providers with `tokens_per_minute` set (Groq: 8,000). The knowledge agent is offered 10 tools (`workers/knowledge.TOOLS`), gets 4 rounds and 2 for its retry (worst case 6 requests, was 12). The last round of every tool loop gets the results as one plain message. An `output_parse_failed` 400 is sent once more.
- **Why:** (a) costs money for a problem of pacing and size. (b) waits even when there is room. Measured after: 4 requests, about 8,900 tokens, about 43 seconds per question, no refusals.
- **Cost if wrong:** A question that needs more than three lookups is answered "not held" for the rest. A busy minute makes the AI tab wait up to 60 seconds before sending. Pacing is per process; another process using Groq at the same moment is only seen after the next reply's header, and a 429 then still gets its one `retry-after` wait.
