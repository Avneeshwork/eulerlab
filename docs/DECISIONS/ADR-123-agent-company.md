# ADR-123: The agents become a company with departments, managers and goals, built natively

- **Context:** On 2026-11-02 the operator asked to run the agent network the way Paperclip runs agents: each agent an employee, managers above them who assign and ask for work, and the operator as CEO who reviews and approves the final work. They also asked for goals for every agent and a calendar of agents' work in the UI. Research 141 compared Paperclip, CrewAI's hierarchical process and LangGraph's supervisor pattern.
- **Options:** (a) Run Paperclip beside eulerlab (Node, TypeScript, Postgres; agents are coding CLIs with a shell). (b) Pilot Paperclip on a copy. (c) Build Paperclip's model natively on the agent runtime.
- **Choice:** (c), the operator's choice on 2026-11-02 (recommended). Phase 1 only: `config/org.yaml` (CEO, three departments, their heads on paper with `running: false`, the gate outside the chart), `reports_to` on every agent definition, `config/company.yaml` (company and department goals, all `proposed`), `agents/org.py` and `agents/calendar.py`, `GET /api/agents/org` and `GET /api/agents/calendar`, and the AI tab's Org chart and Calendar views. Tickets, manager workers, the CEO desk and hiring are Phases 2 to 5 (T-4397 to T-4400).
- **Why:** eulerlab already had specs, budgets, schedules, an inbox and a hash-chained log. Paperclip's local adapters run unsandboxed, which would bypass `agents/boundaries.py` and let an agent reach the gate, the ledger or the holdout; reviews also found it checks permissions, not correctness. The calendar reads the launchd job list and the Makefile recipes, so it cannot show a schedule that does not run.
- **Cost if wrong:** If the native build lags Paperclip's features, the parity list in the design doc says which; Paperclip's `http` adapter could still drive these agents later without opening a shell. Nothing in Phase 1 acts: no manager runs and no goal is operator-set until the operator approves it (S-058).
