# ADR-117: Forward testing is a gate PROMOTE plus a paper deployment the operator starts

- **Context:** The deploy preflight said "the forward-test stage is not built (T-3311), so nothing can reach it", and a lab hypothesis that passed the gate could not be deployed at all, because deployments took only registry strategies. The operator asked on 2026-11-01 for this stage, and on 2026-11-02 chose to start each forward test by hand rather than automatically on PROMOTE.
- **Options:** (a) Store a stage field and move strategies through it. (b) Derive the stage from records that already exist: the gate's ledger entry and the deployment folders. (c) Start a paper deployment automatically on PROMOTE.
- **Choice:** (b), without (c). `forward.py`: `promoted` is the latest gate verdict in the ledger being PROMOTE (a later KILL replaces it); `forward_testing` adds an active paper deployment started on or after that day; `live` is an active live deployment. A promoted hypothesis (`H-NNNN`) deploys to paper as its card's one configuration, built by `codegen.build_one`. A card with several configurations is refused, because choosing one after the gate is a selection the gate never priced. The forward record (days, Sharpe, drawdown against the ledger's backtest Sharpe) is `GET /api/deploy/forward`. Leaving the stage reads `forward_test:` in `mandate.yaml`; it is "not set" until the operator writes it. Proposed for the operator: `min_days: 60`, `min_sharpe_ratio_of_backtest: 0.5`, `max_drawdown: 0.25`.
- **Why:** A stored stage can disagree with the evidence; a derived one cannot. The same builder from lab to validation to paper means the paper book is the strategy that was judged.
- **Cost if wrong:** Nothing has passed the gate yet, so the stage is untested on a real promotion. Sixty days at Sharpe 1 has a wide error band, so the proposed rule screens out disasters, not luck. The preflight's credential check also stops asking for `ZERODHA_ACCESS_TOKEN` in `.env`, which the login flow never sets (HISTORY #58).
