# ADR-131: The research agent searches CORE and Semantic Scholar too, and reads keys under the operator's names

- **Context:** The operator added free keys for OpenAlex (`OPEN_ALEX_API_KEY`), CORE (`CORE_API`) and Semantic Scholar (`Semantic_API`) (T-4413). The code read only `OPENALEX_API_KEY`, so the OpenAlex key was unused (HISTORY #69), and CORE and Semantic Scholar were not sources (ADR-129 left them out for want of keys).
- **Options:** (a) Ask the operator to rename the keys in `.env`. (b) Accept both the standard name and the operator's spelling, and add both services as sources. (c) Add only one of them.
- **Choice:** (b). `paper_search.api_key(names)` loads `.env` and returns the first name holding a value. `core` searches CORE v3 with every content word of the topic required in the abstract; `semantic_scholar` uses its relevance search in economics and business. Keys go in headers (`Authorization: Bearer`, `x-api-key`), never the URL. `paper_search.SPACING` waits 6 s after CORE and 1 s after Semantic Scholar; a Semantic Scholar 429 is retried twice. Both are listed in `config/agents/research.yaml`; `DEFAULT_SOURCES` is unchanged.
- **Why:** (a) is a step the operator would have to remember on every machine. Both services return abstracts, which SSRN and NBER through OpenAlex and Crossref mostly do not: on 2026-11-03 they added 7–10 papers a topic each, most with abstracts (research 146).
- **Cost if wrong:** Two more services each search costs time (about 7 s of waiting per topic) and tokens of a daily allowance (CORE 1,000, A-100). Results from them that are off topic still take ranking slots, though the topic score keeps them low.
