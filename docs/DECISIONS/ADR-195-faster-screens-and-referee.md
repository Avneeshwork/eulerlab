# ADR-195 — Screens price each fill once, run across cores, and the slow engine referees a sample

**Date:** 2026-11-14. **Status:** accepted; operator's "do this also" on 2026-11-14 (#167). Measured on made-up data only.

- **Context.** `make fast-eval-bench` measured 2.9 s a rule on the Mac, one process (research 192). Search depth is where machine research beats people. Profiling a 300-stock, 1,000-session made-up panel: once the field tables exist, about 60% of a screen was the cost model, because every trade's `costs` property was recomputed five or more times (the screen, the summary, each bias check, the daily series), each a Decimal-rounded fee lookup. Issue #167.
- **Options.** (a) Rewrite the books as matrix operations for whole populations. (b) Remove the repeated work first (each trade's costs once; each fill's fee once a process), then a process pool, with the slow engine re-scoring a sample. (c) A GPU.
- **Choice.** (b). `cross_section.Trade.costs` and `other_data_screen.Swing` costs are cached per object; `screen_common.intraday_fee` and `other_data_screen.delivery_fee` are memoised (pure functions of price, quantity, side and day). `fast_eval.screen_many(specs, engine, workers=)` screens contiguous chunks across processes (fork on Linux, spawn on macOS) and returns results in input order, byte-identical to one process; a pool that cannot start falls back to one. `fast_eval.referee` re-screens the engine rules whose fingerprint hash falls in a share (1% by default) with the slow `rule_engine.Engine` and appends any difference to `data/derived/parity.jsonl`. `evaluate(..., workers=)` and `make fast-eval-bench WORKERS=0` use the pool.
- **Why.** Exact by construction: the same arithmetic, done once. On the made-up panel a new rule went from 1.5 s to 0.42 s after its tables were built (0.23 s when its fills repeat earlier ones), and 4 processes screened 2.7 times as many rules as one. Real throughput must be measured on the Mac.
- **Cost if wrong.** This is not the 100x the issue asks for: books are still Python loops, so a population is still screened rule by rule (T-4629). Evolve screens one candidate at a time, so it gains from the caches but not the pool until it screens a generation as a batch. The referee covers engine rules only; language-v2 rules have no independent slow path. The memo grows to a million fills a process. Nothing schedules the referee yet.
